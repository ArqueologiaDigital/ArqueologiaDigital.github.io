Andei avançando na pesquisa sobre esse equipamento e em breve farei uma postagem com todos os detalhes.

Mas, em resumo, nessas últimas semanas voltei a olhar para o arquivo de update de sistema e comecei a conseguir decifrar o método de compressão de dados utilizado. Com a ajuda do RicBit, consegui perceber que trata-se de uma compressão similar aos algoritmos LZ77, LZ78 ou LZW. Sinceramente, eu não tenho nenhuma familiaridade com isso, mas com base no pouco que li até agora, já deu pra desvendar algumas coisas.

A compressão é feita com reuso de trechos de dados repetidos, como uma colcha de retalhos. E parece haver uma alternância entre dados crus separados por bytes marcadores (tipicamente 0xFF a cada 8 bytes raw, mas isso varia de uma forma que ainda não compreendi direito) e substituições de dados que já tenham aparecido recentemente, codificados usando um par de bytes onde 12 bits correspondem ao endereço onde se encontra o trecho a ser copiado dentro de um bloco de 4kbytes, e os outros 4 bits definem qual o tamanho do retalho a ser copiado. Esse comprimento é de no mínimo o 3 bytes (codificado com os bits 0000), pois é o comprimento mínimo que faria ainda sentido do ponto de vista de compressão: substituir 3 bytes gastando 2 bytes para a codificacao. Vi casos de substituicoes de 7 bytes (codificado como o número 4 => bits 0100). Suponho que seja possível fazer uma substituicao mais longa, de 8 bytes (codificado como 5 / 0101), mas nao sei dizer qual o comprimento máximo das substituicoes, pois suspeito que o valor F / 1111 seja justamente usado como marcador separando blocos consecutivos de dados raw. Talvez E / 1110 tenha algum outro significado especial também. Eu precisaria investigar / procurar mais casos de exemplo pra ter certeza.

Encontrei no binário de update algumas strings que sei onde aparecem na interface de usuário do aparelho. E como essas strings continham esses bytes e words de controle da compressão, resolvi experimentar fazendo patches no binário. Fiquei com medo de brickar o aparelho inicialmente, mas depois de pensar bastante, concluí que o mecanismo de carga de updates de firmware fica em ROM e portanto não pode ser corrompido e sempre estará disponível. Então cruzei os dedos e tentei carregar um update modificado. Não bricou! E apareceram as strings modificadas na tela.

Ao experimentar com as words que codificam as substituicoes, eu inicialmente achava que os 12 bits eram um offset relativo dentro de uma "janela deslizante" dos últimos 4kbytes de dados descomprimidos. Mas depois de alguns testes percebi empiricamente que são endereços absolutos. Então minha teoria atual é de que o algoritmo de descompressão tem um buffer de 4k bytes inicialmente não inicializado e que ao longo da descompressão dos primeiros 4k, provavelmente se usa apenas enderecoes menores do que o da posicao atual do ponteiro de escrita do dados descomprimidos. E que ao passar dos primeiros 4k, esses 12 bits podem ter qualquer valor de modo que quando forem maior que o ponteiro dentro do bloco de 4k atual, vao ser usados os dados do bloco anterior de memória.
